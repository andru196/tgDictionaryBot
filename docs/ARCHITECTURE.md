# Личный дневник в Telegram → HTML-отчёт

Архитектурный план сервиса на .NET 10.

Сопутствующие документы: **[EXTENSIBILITY.md](EXTENSIBILITY.md)** — как добавляется новый вид записей, **[MODELS.md](MODELS.md)** — выбор модели и как его измерить, **[MULTI-SUBJECT.md](MULTI-SUBJECT.md)** — несколько наблюдаемых людей и изоляция их данных.

---

## 1. Что строим

Ты в течение дня кидаешь в свой приватный канал текст и голосовые. Ничего не структурируешь, не нажимаешь кнопок, не выбираешь категорию — просто говоришь. Потом запускаешь анализ: он забирает всё непрочитанное, расшифровывает речь, раскладывает по категориям локальной LLM, считает статистику и выдаёт один самодостаточный HTML.

Стартовые виды записей — еда, симптомы ЖКТ, идеи, вопросы. Ключевое требование к конструкции: **пятый и десятый вид добавляются без правки существующего кода** (см. [EXTENSIBILITY.md](EXTENSIBILITY.md)).

**Наблюдаемых людей может быть несколько** — каждый со своим каналом, своей базой, своими окнами и своим отчётом. Это не «мультиарендность на будущее», а требование с последствиями по всей системе: смешать пищевую статистику двух человек — значит получить бессмысленные цифры и утечку медданных одновременно. Как устроена изоляция — в [MULTI-SUBJECT.md](MULTI-SUBJECT.md).

## 2. Транспорт: свой канал вместо бота

Отказ от бота убирает то самое ограничение, которое ломало исходный замысел. Bot API хранит непрочитанные апдейты **24 часа** — с ним «включу раз в год» было невозможно. Личный аккаунт через MTProto (`WTelegramClient`) читает **всю историю** и скачивает медиа любой давности: Telegram хранит их в облаке, а `file_reference` при необходимости обновляется перезапросом сообщения.

**Следствие: always-on демон больше не нужен.** Два процесса схлопываются в одно консольное приложение, которое ты запускаешь когда захочешь. Режим `--watch` остаётся, но как удобство, а не как условие того, что данные не потеряются.

```
Telegram: канал «я»    канал «мама»    канал «…»
        │  MTProto, pull по курсору — свой на каждого
        ▼
   Diary.Cli ──► своя SQLite + свой data/<subject>/voice/ на субъекта
        │
        ├─ Whisper ──► транскрипты          общие: модели, промпты,
        ├─ LM Studio ──► структурированные   пороги по умолчанию
        ├─ детерминированная аналитика       раздельное: данные, курсоры,
        └─ HTML-отчёт — свой на субъекта     окна, retention, отчёты
```

### 2.1 Какие именно чаты

Конфигом задаётся список субъектов, у каждого свой `Peer`. Поддерживаются три вида чатов, но они не равноценны:

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Приватный канал** (только ты) | чистое пространство, ничего лишнего, автоудаление безопасно | писать чуть менее привычно, чем в «Избранное» |
| Приватная группа с собой | привычный чат, reply нативный | легко случайно кого-то добавить |
| Saved Messages | удобнее всего кидать, шаринг из любого приложения | там же твои пересылки и заметки — **автоудаление опасно** |

**Рекомендация — приватный канал.** Главный аргумент именно в удалении: раз есть переключатель, который стирает сообщения, пространство должно содержать только дневник и ничего больше. Промахнуться в «Избранном» стоит дорого и необратимо.

**Но чат субъекта не определяет.** Определяет **id отправителя**: в общую группу могут писать несколько человек, в чужой канал может влезть кто угодно, а пересланное сообщение вообще написано третьим лицом. Поэтому запись маршрутизируется по паре `(PeerId, SenderId)`, где решающий — второй:

```csharp
public interface ISubjectRouter
{
    SubjectRouting Route(IncomingMessage message);   // Assigned(subject) | Unassigned(reason)
}
```

Три правила, которые из этого следуют:

1. **`SenderId` — числовой user id, не `@username`.** Username меняется, id — нет.
2. **Неопознанный отправитель попадает в карантин, а не в мусор и не «к ближайшему».** Молча выбросить — потерять запись; молча присвоить — загрязнить чужую статистику. Такие сообщения складываются как `Unassigned` и показываются в `diary status` с подсказкой, какой `SenderId` добавить в конфиг.
3. **Пересылки по умолчанию пропускаются.** Переслать себе чужой рецепт — не значит его съесть. Поведение настраивается (`Forwarder` / `OriginalAuthor` / `Skip`), дефолт — `Skip`.

Частный случай: в канале сообщения идут от имени канала, и `SenderId` там может отсутствовать. Тогда работает привязка по peer — но только если канал объявлен эксклюзивным для субъекта.

Конфиг валидируется на старте: ключи субъектов уникальны, пары `(Peer, SenderId)` не пересекаются, а субъект, захватывающий чат целиком (без указания отправителей), не может делить этот чат с другими.

### 2.2 Курсор: сервис сам решает, что прочитано

Состояние прочтения — локальное, в базе субъекта, а не в Telegram:

```csharp
public sealed record SyncCursor(
    long PeerId,
    long LastProcessedMessageId,   // все сообщения с id ≤ этого уже забраны
    DateTimeOffset LastSyncAtUtc,
    long HistoryBackfilledTo);     // докуда докопали историю при первом запуске
```

- Инкрементальный проход: `messages.GetHistory(peer, min_id: LastProcessedMessageId)`.
- Первый запуск делает **бэкфилл** — вычитывает историю до начала канала, порциями, соблюдая `FLOOD_WAIT`.
- Идемпотентность через `UNIQUE (PeerId, TelegramMessageId)`: повторный проход не создаёт дублей.
- **Правки учитываются.** Отредактированные сообщения ловятся по `edit_date > CapturedAt` и переразбираются: старые извлечённые записи помечаются `Superseded`, создаются новые. Иначе исправленная задним числом опечатка в еде осталась бы в статистике навсегда.
- Опционально `messages.ReadHistory` — чтобы непрочитанный бейдж не висел на канале. Настраивается отдельно от курсора и на логику не влияет.

Курсор двигается **только после успешного сохранения** сообщения и его медиа в локальную БД, в одной транзакции. Падение посреди синхронизации означает повтор нескольких сообщений, а не потерю.

### 2.3 Переключатель удаления

```jsonc
"Retention": {
  "Mode": "Keep",                     // Keep | React | Delete
  "RequiresState": "Extracted",       // удалять только полностью разобранное
  "MinAge": "7.00:00:00",             // и не раньше, чем через неделю
  "KeepFailed": true,                 // Failed не удаляется никогда
  "DryRun": true                      // первый прогон только печатает список
}
```

- `Keep` — не трогать (по умолчанию).
- `React` — поставить ✅ на обработанное. Видно с телефона, что уже учтено, ничего не теряется.
- `Delete` — `messages.DeleteMessages` с `revoke`.

Удаление необратимо, поэтому переключатель обвешан предохранителями: стирается только то, что доведено до `Extracted`, имеет локальную копию текста и скачанный аудиофайл, старше `MinAge`, и не в `Failed`. Каждое удаление пишется в таблицу `DeletionLog` — id, дата, хэш содержимого, длина транскрипта. Даже если файл потом потеряется, будет видно, что именно исчезло и когда.

`DryRun: true` стоит по умолчанию: первый прогон печатает, что бы он удалил, и ничего не делает.

Режим задаётся **на каждого субъекта отдельно**. Себе можно поставить `Delete` и держать канал пустым; в чужом канале удалять чужие сообщения — решение чужое, и по умолчанию там `Keep`.

### 2.4 Риски личного аккаунта

Это user API, не бот. Практические следствия, которые заложены в реализацию: нужны `api_id`/`api_hash` с my.telegram.org; файл сессии — секрет (в `.gitignore`, шифруется паролем); при 2FA логин спросит пароль один раз; `FLOOD_WAIT_X` обрабатывается ожиданием, а не ретраем в лоб; скачивание медиа идёт последовательно, без распараллеливания на десять потоков. Чтение собственного канала в один поток — нагрузка, неотличимая от обычного клиента.

Ядро — горизонтальные слои. Функциональность — **вертикальные модули**, каждый со своим доменом, извлечением, статистикой и секцией отчёта.

```
│   ├── Diary.Application/                   ← порты, оркестрация, реестр модулей,
│   │                                          реестр субъектов и маршрутизация по отправителю

│   ├── Diary.Modules.Notes/                 ← идеи и вопросы
│   │                                          (сон, лекарства, тренировки — сюда же, новыми проектами)
│   │

│   ├── Diary.Infrastructure.Persistence/    ← EF Core 10 + SQLite

│   ├── Diary.Infrastructure.Llm/            ← LM Studio через Microsoft.Extensions.AI
│   ├── Diary.Infrastructure.Reporting/      ← Razor-компоненты → HTML

└── tests/

    ├── Diary.Application.Tests/
```

Правило зависимостей:

```
Cli ──► Application ──► Domain

 │           │              │
```

## 4. Доменная модель

### 4.1 Два уровня

**`CapturedMessage`** — сырьё, ровно как пришло, плюс транскрипт. Смысл не меняется никогда, только состояние обработки. Это архив: даже если разбор окажется мусорным, исходник цел и переразбор бесплатен.

```csharp
public sealed class CapturedMessage
{
    public MessageId Id { get; }
    public long PeerId { get; }
    public long TelegramMessageId { get; }         // UNIQUE вместе с PeerId
    public DateTimeOffset SentAtUtc { get; }
    public DateTimeOffset? EditedAtUtc { get; }
    public MessageKind Kind { get; }               // Text | Voice | VideoNote | Photo
    public string? Text { get; }
    public VoiceAsset? Voice { get; }
    public long? ReplyToTelegramMessageId { get; }
    public IReadOnlyList<string> Hashtags { get; }
    public Transcript? Transcript { get; }
    public ProcessingState State { get; }
    public string? FailureReason { get; }
}

public enum ProcessingState { Captured, Transcribed, Extracted, Failed, Skipped, Superseded }
```

**`DiaryEntry`** — смысл. Одно сообщение даёт **1..N** записей: «съел борщ, кстати идея — линтер для промптов, и надо загуглить чем span отличается от memory» — три записи из одного голосового.

```csharp
public sealed class DiaryEntry
{
    public EntryId Id { get; }
    public MessageId SourceMessageId { get; }      // всегда можно вернуться к исходнику
    public string ModuleKey { get; }               // "gi" | "notes" | …
    public CategoryKey Category { get; }           // "meal" | "symptom" | "idea" | "question"
    public DateTimeOffset OccurredAtUtc { get; }   // ≠ время отправки: «вчера вечером ел…»
    public TimeCertainty TimeCertainty { get; }    // Exact | Resolved | Approximate
    public string RawFragment { get; }
    public Confidence Confidence { get; }
    public JsonDocument Payload { get; }           // типизированная часть модуля
    public string ExtractorVersion { get; }        // модель + версия промпта
}
```

Одна сущность на все виды записей — намеренно. Специфика лежит в `Payload` и типизируется модулем через `Payload.Deserialize<MealPayload>()`. Новый вид записей не требует ни новой таблицы, ни миграции. Как это не превращается в кашу — в разделе 5.

### 4.2 Модуль ЖКТ

```csharp
public sealed record MealPayload(IReadOnlyList<FoodItem> Items, MealType Type);
public sealed record FoodItem(
    string CanonicalName,                          // "картофель жареный"
    string RawName,                                // "жарёха", как сказано
    Quantity? Quantity,
    IReadOnlySet<FoodTag> Tags);

public sealed record SymptomPayload(
    SymptomKind Kind, Severity Severity,
    TimeSpan? Duration, string? SuspectedFoodMention);   // «после вчерашнего борща»

[Flags] public enum FoodTag { Fatty, Fried, Spicy, Acidic, Dairy, Gluten, Caffeine,
                              Alcohol, Carbonated, Legumes, RawVegetables, Sweet, Processed }
public enum SymptomKind { Reflux, Heartburn, Bloating, Gas, Diarrhea, Constipation,
                          Nausea, AbdominalPain, Belching, Other }
public readonly record struct Severity;            // 0..10, валидируется в конструкторе
```

### 4.3 Доменные сервисы — детерминированные, без LLM

```csharp
public interface IMealSymptomLinker          // три уровня связывания, раздел 8
public interface IGiStatisticsCalculator     // lift, Фишер, тренды — раздел 9
public sealed class ExposureWindowCalibrator // подстройка окон по подтверждённым связкам
public sealed class FoodCanonicalizer        // «жарёха» → «картофель жареный»
public sealed class RelativeTimeResolver     // {-1 день, вечер} + SentAt → абсолютный UTC
```

Принцип, на котором держится доверие к отчёту: **модель извлекает структуру из речи, считает обычный код.** Локальная LLM невоспроизводима между запусками и плохо считает; статистика обязана быть одинаковой при повторном прогоне и объяснимой построчно. Побочный выигрыш — самая ценная логика покрывается unit-тестами без единого HTTP-вызова.

## 5. Хранение: гибрид вместо крайностей

Требования конфликтуют. Расширяемость хочет схему без миграций; статистика за произвольный срок хочет индексы и нормализацию. Крайности плохи обе: таблица на каждый вид записей — миграция на каждую новую идею; всё в JSON — статистика за год превращается в полный скан с разбором документов.

Решение — **разделить по частоте запросов**. Схема ниже — внутри базы **одного субъекта**: у каждого человека свой файл `data/<subject>/diary.db`, поэтому колонки `SubjectId` в таблицах нет и запрос физически не может достать чужие данные ([MULTI-SUBJECT.md](MULTI-SUBJECT.md), раздел 2).

```
entries            общие поля колонками + payload JSON       ← все модули, без миграций
  ├─ id, source_message_id, module_key, category
  ├─ occurred_at_utc  ← INDEX, по нему режутся любые периоды
  └─ payload (JSON)

gi_meal_items      проекция: одна строка на продукт          ← горячий путь ЖКТ
  ├─ entry_id, occurred_at_utc ← INDEX
  ├─ canonical_name ← INDEX
  └─ tags (битовая маска) ← INDEX

gi_symptoms        проекция: одна строка на симптом
  ├─ entry_id, occurred_at_utc ← INDEX
  ├─ kind, severity
  └─ …

gi_links           связки еда↔симптом с типом и весом
```

Проекции строит сам модуль через `IEntryProjector`, в той же транзакции, что и запись. Модуль, которому хватает JSON-запросов (`json_extract` в SQLite умеет), проекций не заводит вовсе и остаётся чистым кодом без единой миграции. ЖКТ проекции заводит, потому что это его горячий путь — и получает статистику за любой период на индексах.

Итог: расширяемость не оплачена скоростью, а скорость — миграциями на каждый чих.

## 6. Пайплайн

```
Telegram ──sync──► [Captured] ──speech──► [Transcribed] ──llm──► [Extracted] ──retention──► ✅/🗑
                       │                       │                     │
                  data/voice/*.ogg        транскрипт в БД      DiaryEntry[] + проекции
```

Каждый шаг **идемпотентен** (работает только со своим входным состоянием), **атомарен** (состояние двигается в одной транзакции с результатом), **возобновляем** (упало на 300-м голосовом из 500 — перезапуск продолжит с 301-го) и **прослеживаем** (рядом с результатом пишется модель и версия промпта).

Последнее даёт бесплатную суперспособность, которая тут особенно к месту: сменил модель — запустил

```bash
diary reprocess --from-state Transcribed --since 2026-01-01
```

и вся история переразобралась новой моделью. Сырьё и транскрипты не тронуты, потому что они не зависят от того, какая LLM стоит сегодня. Это прямой ответ на «Qwen3-8B слабовато»: смена модели не требует переписывать код и не обесценивает накопленные данные.

Параллелизм разный по шагам: транскрипция упирается в GPU (1–2 потока), извлечение — в очередь LM Studio (2–4), скачивание медиа — последовательно из-за лимитов Telegram. Числа в конфиге.

## 7. Понимание речи

Порт намеренно шире, чем «распознавание»:

```csharp
public interface IUtteranceReader
{
    Task<Utterance> ReadAsync(VoiceAsset audio, CancellationToken ct);
}
public sealed record Utterance(string Transcript, float Confidence, Prosody? Prosody);
```

**Реализация по умолчанию — каскад:** декодер OGG/Opus → PCM 16 кГц → Whisper (`large-v3-turbo`, язык `ru` фиксирован, initial prompt со словарём «изжога, рефлюкс, вздутие, отрыжка» — заметно поднимает точность на терминах). Whisper специализирован под ASR и в русском обыгрывает универсальные модели своего размера; транскрипт всё равно нужен отдельно — для архива, поиска и переразбора без повторного прогона аудио.

**Альтернативная реализация — нативное аудио:** модель, принимающая звук напрямую (класс Omni). Даёт то, что теряет транскрипт: интонацию, паузы, неуверенность в голосе. Подключается той же строчкой в DI, когда LM Studio даст стабильный аудио-вход для выбранной модели — проверять надо на месте, поддержка модальностей там отстаёт от релизов моделей.

**Гибрид, если понадобится точность:** слова берутся у Whisper, а фрагменты с низкой `Confidence` переслушиваются аудио-моделью. Дороже, но применяется к единицам процентов записей.

Аудио сохраняется навсегда (десятки КБ на сообщение) — чтобы переслушать спорное место и чтобы переразбор новой моделью был возможен даже после `Retention: Delete`.

## 8. Связывание «еда → симптом»

Reply — самый точный сигнал, но рассчитывать на него нельзя: ты пишешь на ходу и свайпать будешь не всегда. Поэтому связывание **трёхуровневое**, и уровень фиксируется в данных:

```csharp
public enum LinkKind { Reply, TextualReference, TemporalWindow }
public sealed record MealSymptomLink(EntryId MealId, EntryId SymptomId, LinkKind Kind, double Weight);
```

| Уровень | Откуда | Вес | Как часто бывает |
|---|---|---|---|
| `Reply` | ответ на сообщение о еде | 1.0 | редко, но железно |
| `TextualReference` | «после вчерашнего борща» → `SuspectedFoodMention` при извлечении, резолвится поиском ближайшего подходящего приёма | 0.8 | иногда |
| `TemporalWindow` | попадание в окно экспозиции; вес убывает к краям окна | 0.3–0.6 | основная масса |

Окна разные под симптом, потому что одно окно на всех даёт мусор:

| Симптом | Окно после приёма |
|---|---|
| Рефлюкс, изжога, отрыжка | 0–4 ч |
| Вздутие, газы | 1–8 ч |
| Диарея, боль | 2–24 ч |
| Запор | 8–48 ч |

### Явные связки калибруют окна для всех остальных

Здесь редкие reply отрабатывают непропорционально своей частоте. `ExposureWindowCalibrator` берёт **только** подтверждённые связки (`Reply` + `TextualReference`), строит эмпирическое распределение задержек по типу симптома и предлагает окна вместо табличных:

> По 14 подтверждённым связкам изжога наступает через 1 ч 40 м ± 50 м. Предлагаемое окно: 0:30–3:00 вместо дефолтного 0:00–4:00.

Дефолтные окна взяты из общей физиологии, а откалиброванные — твои. Сузившееся окно режет ложные совпадения по всей остальной выборке. То есть каждый свайп reply улучшает статистику не одной записи, а всех — но система работает и без единого свайпа.

Уровень связи виден в отчёте: подтверждённые пары помечаются отдельно, чтобы было понятно, где вывод опирается на факт, а где на предположение о времени.

## 9. Статистика ЖКТ за произвольный период

Считается в модуле, детерминированно, покрыто тестами.

```csharp
public sealed record GiStatsQuery(
    DateRange Period,                     // любой: день, неделя, «с 1 января», всё время
    Granularity Granularity,              // Day | Week | Month — для трендов
    ExposureWindowPolicy Windows,         // табличные или откалиброванные
    int MinSupport = 3,
    double MinLift = 1.5,
    FoodFilter? OnlyFood = null,          // «покажи всё про жареную картошку»
    DateRange? CompareTo = null);         // сравнение с другим периодом
```

### 9.1 Метрики

Для каждой пары (продукт `F`, симптом `S`) внутри периода:

```
a  = приёмов F, после которых в окне был S
b  = приёмов F без симптома
p₁ = a / (a + b)                                    — P(S | ел F)
p₀ = базовая частота S по всем приёмам ЭТОГО периода — P(S)
lift = p₁ / p₀
```

Плюс односторонний **точный тест Фишера** → p-value, медианная задержка, средняя тяжесть. В подозреваемые пара попадает при `support ≥ 3` и `lift ≥ 1.5`; всё остальное показывается с пометкой «данных мало» — не как вывод, а чтобы было видно, чего именно не хватает.

Зеркально — список **переносимых** продуктов: `support ≥ 5`, `lift ≤ 0.7`. На практике полезнее списка подозреваемых, потому что отвечает на вопрос «что есть», а не только «чего избегать».

### 9.2 Два уровня: блюда и свойства пищи

Конкретный «борщ» за месяц встретится три раза — статистики не будет. Тег `Fried` — сорок раз, `Caffeine` — шестьдесят. Поэтому корреляции считаются **одновременно по продуктам и по тегам**: теги дают сигнал уже на второй неделе, продукты — через пару месяцев. Без второго уровня отчёт первые месяцы пустой.

### 9.3 Три вещи, которые ломаются на произвольных периодах

Это не абстрактная аккуратность — без них цифры будут врать именно на коротких интервалах:

1. **Загрузка с запасом.** Симптом 1 января в 02:00 вызван ужином 31 декабря. Данные грузятся с `Period.Start − maxWindow`, но в знаменатель попадают только приёмы внутри периода. Иначе первые часы любого периода систематически выглядят «чистыми».
2. **Базовая частота — своя для периода.** `p₀` считается по тому же интервалу, иначе `lift` сравнивает несравнимое: неделю обострения с годовым фоном.
3. **Множественные сравнения.** Чем короче период, тем меньше `n` и тем легче получить случайное «открытие». Порог `MinSupport` не смягчается на коротких периодах, а в отчёт выводится честное предупреждение с числом проверенных гипотез.

### 9.4 Тренды и сравнение

- `Granularity` даёт разбивку по дням/неделям/месяцам: частота симптомов, средняя тяжесть, доля «чистых» дней.
- `CompareTo` сравнивает два периода: `--from 2026-07-01 --to 2026-07-31 --compare-to previous`.
- Отдельный сценарий — «стало ли лучше, когда я убрал жареное»: `--split-at 2026-06-01` делит историю по дате и сравнивает половины.

### 9.5 Вывод

Статистика — самостоятельная команда, а не только кусок отчёта:

```bash
diary stats gi --from 2026-01-01 --to 2026-12-31 --group-by month
diary stats gi --food "картофель жареный" --all-time
diary stats gi --period month --compare-to previous --format json
diary stats gi --calibrate-windows            # показать предложенные окна
```

`--format html|json|csv|table`. JSON и CSV — чтобы утащить в Excel или в свой скрипт, не переписывая ничего.

## 10. Слой LLM

Подробности выбора модели, критерии и eval-харнесс — в **[MODELS.md](MODELS.md)**. Здесь только то, что относится к архитектуре.

**Транспорт.** LM Studio отдаёт OpenAI-совместимый API. Берём `Microsoft.Extensions.AI` (`IChatClient`) поверх официального `OpenAI` SDK с подменённым `Endpoint`. Модули про OpenAI не знают — они видят `IStructuredCompletion`.

**Разные модели на разные шаги.** Задачи неравнозначны: сегментация проста, извлечение требует качества, ответы на вопросы — максимума. Роль → модель задаётся конфигом:

```csharp
public enum LlmRole { Segmentation, Extraction, Answering }
public interface IChatClientFactory { IChatClient For(LlmRole role); }
```

Это прямо отвечает на «8B слабовато»: тяжёлую модель ставим только туда, где она нужна, а не на весь пайплайн.

**Два прохода вместо одного.** Сегментация (разбить сообщение на фрагменты, назначить категорию) отделена от извлечения (своя схема и свой узкий промпт на категорию). Модель среднего размера заметно хуже делает «раздели И извлеки всё сразу» на длинных голосовых; узкий промпт для еды не содержит ни слова про идеи.

**Structured output, а не парсинг текста.** `response_format: json_schema`, схема генерируется из C#-DTO — контракт и код не разъезжаются. Невалидный JSON → один ремонтный ретрай с текстом ошибки валидации → иначе запись уходит в `Failed` с сохранённым сырым ответом. Один кривой ответ не роняет прогон.

**Промпты — код.** Embedded resources с версией в имени (`segment.v3.ru.md`), версия пишется в БД рядом с результатом, ревьюятся в PR. Сегментационный промпт **собирается динамически** из зарегистрированных модулей — новый вид записей автоматически появляется в списке категорий (см. [EXTENSIBILITY.md](EXTENSIBILITY.md)).

**Tool calling** — для агентного шага «ответить на накопленные вопросы»: поиск по собственной истории, справочник продуктов, запрос к БД. В основном пайплайне извлечения не используется: там structured output строго надёжнее, потому что задача не агентная, а «текст → схема».

**Что LLM делать не разрешено:** считать, агрегировать, ранжировать, делать выводы «этот продукт тебе вреден».

## 11. Отчёт

**Рендер:** Razor-компоненты + `HtmlRenderer` из `Microsoft.AspNetCore.Components.Web` — статический серверный рендер из консольного приложения. Типобезопасность, snapshot-тесты, переиспользуемые компоненты. Каждый модуль поставляет свою секцию и порядок сортировки; ядро только собирает документ.

**Формат:** **один самодостаточный `.html`**. Инлайн CSS, инлайн SVG, ноль внешних запросов. Открывается офлайн, кладётся в архив, читается с флешки через десять лет. Графики рисуются как SVG прямо из view-модели — никакого Chart.js по CDN.

**ViewModel** строится в `Application`/модулях и не содержит доменных сущностей — только готовые примитивы и предпосчитанные координаты SVG. Шаблон ничего не вычисляет.

Живой пример с выдуманными данными — [`report-sample.html`](report-sample.html).

## 12. Как пользоваться

**Сбор** — ничего не делать. Пишешь и наговариваешь в канал как в заметки.

Необязательные приёмы, каждый из которых что-то улучшает, но ни один не обязателен:

- **reply** на сообщение о еде при описании симптома → железная связка, плюс калибровка окон для всей остальной статистики;
- **хэштеги** `#еда #симптом #идея #вопрос` → детерминированная категория в обход LLM и рабочий fallback, если модель не завелась;
- **тяжесть числом** — «изжога на четвёрку» → `Severity = 4`, иначе модель ставит по прилагательным и шкала плывёт между запусками.

**Разбор:**

```bash
diary sync                                     # все субъекты: забрать новое из каналов
diary run --report                             # sync + speech + extract + отчёт, по всем
diary report --subject me --period week --open
diary report --subject mom --from 2026-01-01 --to 2026-12-31
diary stats gi --subject mom --all-time --group-by month
diary reprocess --all-subjects --from-state Transcribed --since 2026-06-01
diary retention --subject me --mode delete --dry-run   # посмотреть, что удалилось бы
diary status                                   # таблица состояний по всем субъектам
diary watch                                    # опциональный режим «висеть и подхватывать»
```

Без `--subject` команды чтения и разбора идут по всем субъектам из конфига, а отчёты пишутся отдельными файлами. Команды, которые **что-то меняют в Telegram** (`retention`), требуют `--subject` явно — «удалить у всех сразу» не должно набираться случайно.

## 14. Где здесь SOLID

| Принцип | Как проявляется |
|---|---|
| **SRP** | синхронизация не знает про Whisper, Whisper не знает про LLM, статистика не знает про HTML. Ни один класс не держит два этапа. |
| **OCP** | новый вид записей = новый модуль + регистрация. Существующие файлы не редактируются, включая промпт сегментации — он собирается из реестра. |
| **LSP** | `IUtteranceReader` подменяется с Whisper на аудио-модель, `IMessageSource` — с MTProto на что угодно, без изменений выше. |
| **ISP** | порты узкие: `IVoiceStorage` не умеет читать текст, `IUtteranceReader` не умеет качать файлы. Никаких `IDiaryService` на двадцать методов. |
| **DIP** | модули и `Application` зависят только от интерфейсов; реализации подставляются в композиционном корне. |

Сверх аббревиатуры — два разделения, которые ценнее: **недетерминированное отделено от детерминированного** (LLM изолирована в узкой прослойке, вся аналитика чистая и тестируемая) и **сырьё отделено от интерпретации** (переразбор новой моделью не трогает архив).

## 15. Тестирование

| Слой | Как |
|---|---|
| `Domain` | резолв относительного времени, дедуп, состояния |
| `Modules.Gi` | окна, lift, Фишер, калибровка по явным связкам, загрузка с запасом на границах периода, взвешенные связки. Самое ценное — без единого мока. |
| `Application` | фейковые порты в памяти: идемпотентность синхронизации, возобновление после падения, предохранители retention |
| Маршрутизация | сообщения от чужого `SenderId` → карантин, а не в чужую базу; пересылки; канал без отправителя; пересекающиеся конфиги отвергаются на старте |
| `Reporting` | snapshot-тесты (`Verify`): ViewModel → HTML |
| `Llm` | контрактные тесты на **записанных** ответах модели: парсинг, стриппер think-блоков, ремонтный ретрай. Офлайн, в CI. |
| Живая LLM | `[Trait("Category","RequiresLmStudio")]`, из CI исключена |
| Eval | отдельный харнесс для сравнения моделей — см. [MODELS.md](MODELS.md) |

Retention заслуживает отдельного внимания в тестах: это единственное место, где система **удаляет** данные. Проверяется, что не удаляется `Failed`, не удаляется без локальной копии, не удаляется раньше `MinAge`, и что `DryRun` не трогает ничего.

## 16. Приватность

Дневник еды и симптомов — медицинские данные, и они не покидают машину. Это не лозунг, а следствие конструкции: LLM локальная, распознавание локальное, база локальная, отчёт локальный. Наружу идёт один канал — MTProto к Telegram, и то за собственными сообщениями.

- `data/`, `reports/`, `models/`, `*.db`, `*.session`, `*.ogg` — в `.gitignore`, репозиторий публичный.
- `api_id`/`api_hash`/пароль сессии — в user-secrets или переменных окружения.
- Файл сессии равен доступу к аккаунту — с ним обращаться как с паролем.
- Опционально SQLCipher, если ноутбук ездит с тобой.

С появлением второго субъекта добавляется то, чего в однопользовательской версии не было: **это чужие медицинские данные.** Человек должен понимать, что его сообщения читает программа, что расшифровки и выводы хранятся у тебя и что отчёт по нему существует. Технически система это поддерживает — данные каждого лежат отдельно, удаляются одной папкой, отчёты не смешиваются ([MULTI-SUBJECT.md](MULTI-SUBJECT.md)), — но сам факт согласия кодом не решается.

## 17. Порядок работ

| Этап | Результат | Ценность |
|---|---|---|
| **M0** | MTProto-логин, реестр субъектов и маршрутизация по `SenderId`, бэкфилл истории, курсор, SQLite, скачивание голосовых | сырьё под контролем, ничего не теряется и не смешивается |
| **M1** | Whisper + декодер OGG, `diary sync` целиком | голосовые стали текстом |
| **M2** | Реестр модулей, сегментация, модули `gi` и `notes` | текст стал структурой |
| **M3** | HTML-отчёт: идеи, вопросы, лента еды и симптомов | первый читаемый выхлоп |
| **M4** | Статистика: окна, lift, Фишер, теги, произвольные периоды, тренды | ради чего всё затевалось |

| **M6** | Ответы на вопросы с tool calling, экспорт JSON/CSV, новые модули | расширение |
