# Несколько наблюдаемых людей

Как система ведёт дневники нескольких человек и почему их данные не могут перемешаться.

**Субъект** — человек, за которым ведётся наблюдение. У каждого свои сообщения, своя база, свои окна экспозиции, свой отчёт. Наблюдающий (тот, кто запускает `diary`) — не субъект: он может быть субъектом сам, а может просто держать инфраструктуру.

---

## 1. Кто написал важнее, чем куда написал

Соблазнительно считать, что канал определяет человека: «этот канал мой, тот мамин». На практике это разваливается сразу:

- в **общую группу** пишут несколько человек — один peer, разные субъекты;
- в чужой канал **может влезть кто угодно** — админ, приглашённый, ты сам;
- **пересланное** сообщение написано третьим лицом, которого в конфиге нет вовсе;
- в **канале** сообщения идут от имени канала, и отправителя может не быть совсем.

Поэтому запись маршрутизируется по паре `(PeerId, SenderId)`, и решающий — второй:

```csharp
public interface ISubjectRouter
{
    SubjectRouting Route(IncomingMessage message);
}

public abstract record SubjectRouting
{
    public sealed record Assigned(SubjectKey Subject) : SubjectRouting;
    public sealed record Unassigned(UnassignedReason Reason, long? SenderId) : SubjectRouting;
}

public enum UnassignedReason { UnknownSender, Forwarded, NoSenderInChannel, AmbiguousConfig }
```

### Порядок разрешения

1. `SenderId` есть и сопоставлен субъекту → **Assigned**.
2. `SenderId` есть, но не сопоставлен → **Unassigned(UnknownSender)**.
3. `SenderId` нет (пост от имени канала), а чат объявлен `Exclusive` для субъекта → **Assigned** по peer.
4. `SenderId` нет и чат не эксклюзивен → **Unassigned(NoSenderInChannel)**.
5. Сообщение переслано → политика `Forwarded`, по умолчанию **Skip**.

### Три правила, которые из этого следуют

**`SenderId` — числовой user id, а не `@username`.** Username меняется и переиспользуется; числовой id стабилен. В конфиге разрешено писать username для удобства, но при первом запуске он резолвится в id, и дальше живёт именно id — резолвинг при каждом запуске означал бы, что смена ника молча переклеивает дневник на другого человека.

**Неопознанный отправитель уходит в карантин, а не в мусор и не «к ближайшему».** Обе тихие стратегии плохи по-своему: выбросить — потерять запись навсегда, присвоить — навсегда загрязнить чужую статистику (и попробуй потом найди, какие именно строки лишние). Карантин — единственный вариант, который обратим:

```
$ diary status

  me     412 записей   курсор 18422   ✓
  mom    193 записи    курсор  2277   ✓

  ⚠ карантин: 7 сообщений от неизвестных отправителей
      SenderId 555123456  ·  5 сообщений  ·  «Наташа»  ·  первое 2 авг
      SenderId 555987654  ·  2 сообщения  ·  без имени ·  первое 9 авг
    добавь SenderId в Subjects[].Sources[].SenderIds и запусти: diary requeue --unassigned
```

**Пересылки по умолчанию пропускаются.** Переслать себе чужой рецепт — не значит его съесть; переслать статью — не значит задать вопрос. Дефолт `Skip`, альтернативы (`Forwarder`, `OriginalAuthor`) включаются осознанно.

### Валидация конфига на старте

Процесс не поднимется, если:

- ключи субъектов не уникальны;
- пара `(Peer, SenderId)` встречается у двух субъектов;
- субъект объявил чат `Exclusive`, но этот же чат используют другие;
- `DataDirectory` совпадает у двух субъектов.

Всё это — ошибки, которые иначе проявятся не сразу, а через месяц кривой статистикой. `ValidateOnStart` дешевле.

## 2. Изоляция: отдельная база на человека

Два способа развести данные:

| | Общая БД + колонка `SubjectId` | **Отдельная БД на субъекта** |
|---|---|---|
| Изоляция | зависит от каждого `WHERE` | физическая: чужих строк в файле нет |
| Забытый фильтр | смешивает медданные | невозможен |
| «Удали всё про N» | `DELETE` по всем таблицам | удалить папку |
| «Отдай человеку его данные» | выгрузка с фильтрами | отдать файл |
| Кросс-анализ | тривиален | через агрегаты |

Выбран второй. Причина не в производительности, а в характере ошибки: забытый `WHERE SubjectId = …` в статистике — это баг, который не падает, не логируется и выглядит как правдоподобные цифры. Обнаружить его можно через полгода или никогда. Физическая раздельность убирает целый класс таких ошибок ценой одного неудобства — кросс-субъектный анализ теперь требует явного шага, и это скорее плюс.

```
data/
  telegram.session            общая сессия аккаунта
  me/
    diary.db
    voice/2026/08/1734.ogg
  mom/
    diary.db
    voice/…
reports/
  me/2026-08-17-week.html
  mom/2026-08-17-month.html
```

Внутри базы субъекта колонки `SubjectId` нет — она была бы всегда одинаковой. Запрос физически не может достать чужие данные, потому что их нет в файле.

### Как это выглядит в коде

Субъект — это **DI-скоуп**, а не параметр, который надо не забыть передать:

```csharp
public interface ISubjectScopeFactory
{
    ISubjectScope Create(SubjectKey key);   // свой DbContext, свои пути, свои опции
}

// оркестратор
foreach (var subject in registry.All)
{
    await using var scope = scopeFactory.Create(subject.Key);
    await scope.Resolve<SyncHandler>().RunAsync(ct);
    await scope.Resolve<ExtractHandler>().RunAsync(ct);
}
```

Хендлеры, модули и репозитории про субъектов **не знают вообще** — они получают уже настроенный `DbContext` и пути. Ни один метод не принимает `SubjectId`, поэтому его нельзя забыть, перепутать или подставить чужой. Это то же соображение, что и с `Domain` без ссылок на инфраструктуру: правило, которое невозможно нарушить, надёжнее правила, которое надо помнить.

## 3. Что общее, а что личное

| Общее (одно на всех) | Личное (своё у каждого) |
|---|---|
| сессия Telegram | peer'ы и отправители, курсор синхронизации |
| модели LLM и Whisper | база, аудио, отчёты |
| промпты и их версии | таймзона |
| базовый справочник продуктов | алиасы продуктов («жарёха» — не общечеловеческое слово) |
| дефолтные пороги и окна | откалиброванные окна, `MinSupport`, набор модулей, retention |

Два пункта в правой колонке заслуживают отдельного внимания.

**Окна экспозиции обязаны быть личными.** Скорость эвакуации желудка и чувствительность различаются между людьми в разы; у одного изжога через 40 минут, у другого через три часа. Калибровка по подтверждённым связкам ([ARCHITECTURE.md](ARCHITECTURE.md), раздел 8) считается на данных субъекта и применяется только к нему. Общие окна — лишь стартовое приближение из физиологии.

**Набор модулей — личный.** Маме нужен только ЖКТ; идеи и вопросы для неё — шум, а сегментатор, знающий про лишние категории, будет пытаться их находить и ошибаться. `Modules: ["gi"]` сужает и хранение, и промпт сегментации, и отчёт.

## 4. Отчёты

Отдельный файл на субъекта, всегда. Сводного отчёта «все люди на одной странице» нет и не будет по умолчанию: он объединяет медданные разных людей в один документ, который потом пересылается одним движением.

```bash
diary report --period month              # отдельный файл каждому субъекту
diary report --subject mom --period month --open
```

В шапке отчёта — имя субъекта; в имени файла — его ключ. Если понадобится сравнение между людьми (например, семейная реакция на один продукт), это отдельная явная команда, работающая **с агрегатами, а не с записями**: числа `lift` и `support` сопоставить можно, транскрипты чужих голосовых в общий документ попадать не должны.

## 5. Синхронизация нескольких субъектов

Все каналы читаются **одной сессией Telegram** и **последовательно**. Параллельные запросы к одному аккаунту — прямой путь к `FLOOD_WAIT`, а выигрыш нулевой: узкое место здесь не сеть, а транскрипция и LLM.

Порядок такой: сначала синхронизируются все субъекты (быстро, сеть), потом идут тяжёлые шаги по каждому (долго, GPU). Так сырьё оказывается в безопасности раньше, и падение на транскрипции пятого субъекта не отменяет того, что сообщения первых четырёх уже сохранены.

Сбой у одного субъекта не останавливает остальных: ошибка логируется, курсор этого субъекта не двигается, работа продолжается со следующим. Итоговый статус — таблица, а не одно «упало».

## 6. Ограничения, о которых стоит знать заранее

**Один аккаунт видит только то, что видит.** Читать можно те чаты, где твой аккаунт состоит. Если человек хочет вести дневник в своём личном пространстве, к которому у тебя доступа нет, вариантов два: общая группа или его собственный запуск программы со своей сессией. Второй путь система поддерживает — конфиги независимы.

**Несколько сессий возможны, но это уже другая история.** `SessionFile` вынесен в общие настройки, но при необходимости может быть переопределён на субъекта. Логин под чужим аккаунтом — вопрос доверия, а не техники, и по умолчанию такая конфигурация не предполагается.

**Согласие не решается кодом.** Система умеет хранить данные раздельно, удалить всё про человека одной папкой и не смешивать отчёты. Чего она не умеет — понять, знает ли человек, что его голосовые расшифровываются и анализируются. Это данные о здоровье, и разговор про них происходит до первого запуска, а не после.
