# tgDictionaryBot

Личный голосовой дневник в Telegram, который разбирается локальной LLM и превращается в один красивый HTML-файл.

Наговариваешь в свой приватный канал что попало — что съел, что заболело, какая мысль пришла, что надо загуглить. Потом запускаешь анализ: локальный Whisper расшифровывает голосовые, локальная модель в LM Studio раскладывает речь по категориям, детерминированный код считает корреляции «еда → симптом» за любой период, и на выходе получается отчёт.

**Ничего не уходит наружу.** LLM локальная, распознавание локальное, база локальная. Единственное соединение с интернетом — за собственными сообщениями в Telegram.

## Быстрый старт

Прогнать весь пайплайн на выдуманных данных, без Telegram и без учётной записи — нужна только запущенная LM Studio с загруженной моделью:

```bash
dotnet run --project src/Diary.Cli -- sync --source file:samples/messages.jsonl
```

```bash
dotnet run --project src/Diary.Cli -- extract
```

```bash
dotnet run --project src/Diary.Cli -- report --period month --compare --open
```

Для работы с настоящим Telegram: скопировать [docs/appsettings.example.json](docs/appsettings.example.json) в `appsettings.Local.json` рядом с исполняемым файлом, вписать `ApiId`/`ApiHash` с my.telegram.org и свой канал.

## Четыре решения, на которых держится остальное

**MTProto, а не бот.** Bot API хранит непрочитанные апдейты 24 часа — с ним «включу раз в год» было невозможно. Личный аккаунт читает всю историю и качает медиа любой давности, так что always-on демон не нужен: всё живёт в одном консольном приложении, которое запускается когда захочется.

**LLM только извлекает структуру, считает обычный код.** Локальная модель невоспроизводима между запусками и плохо считает. Корреляции, окна экспозиции и точный тест Фишера живут в детерминированном коде и покрыты тестами — статистика обязана быть одинаковой при повторном прогоне.

**Сырьё отдельно от интерпретации.** Сообщения и транскрипты хранятся навсегда, рядом с каждой извлечённой записью пишется модель и версия промпта. Вышла модель получше — `diary reprocess`, и вся история разобралась заново.

**Субъект — это скоуп, а не параметр.** Людей может быть несколько, у каждого своя база. Забытый `WHERE SubjectId = …` — баг, который не падает и выглядит как правдоподобные цифры, поэтому колонки `SubjectId` просто нет: у каждого свой файл БД. Маршрутизация — по id отправителя, неопознанные уходят в карантин.

## Что пока не реализовано

- **Проекции для статистики** (`gi_meal_items`, `gi_symptoms` из плана). Запросы идут по таблице `entries` с индексом на время — для личного дневника этого хватает с запасом; проекции нужны при десятках тысяч записей.
- **Миграции EF Core.** Схема создаётся через `EnsureCreated`; перевести на миграции надо перед первым изменением схемы, иначе накопленные базы придётся пересоздавать.
- **Нативный аудио-вход** (`Speech:Reader = NativeAudio`) — порт есть, реализации нет.
- **Ответы на вопросы через tool calling** и **eval-харнесс** из [docs/MODELS.md](docs/MODELS.md).
- **Telegram-адаптер написан, но не проверен вживую** — нужны `api_id`/`api_hash`. Файловый источник прогнан полностью.
